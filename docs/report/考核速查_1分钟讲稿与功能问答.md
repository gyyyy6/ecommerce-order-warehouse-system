# 课程考核速查：系统总结 + 随机功能问答

> **考核形式**：① 1 分钟介绍数据库系统主要应用场景与功能；② 教师随机就某个功能提问，需**结合实际工作**回答。
> **本稿依据**：本仓库 `README.md`、`docs/01_requirements.md`、`docs/report/report.md`、`docs/acceptance_matrix.md`、`docs/05_performance.md`、`docs/06_concurrency.md`、`docs/report/defense_qa.md`，以及 `sql/`、`app/` 源码。
> **口径**：文中数字均为仓库中已记录的 Linux VM 实测值，回答时说"我在虚拟机上实测得到……"，不要说成理论值；没有实测过的不要编。

## 一、1 分钟口播稿

### 1.1 必说版（约 230 字，正常语速 50~60 秒）

> 我做的是一个面向中小电商的**订单与仓储管理数据库应用**。原来用表格人工登记，数据重复、库存账实不符、订单和物流对不上，所以把客户、商品、分类、订单、明细、物流单统一放进 PostgreSQL，运营和仓储人员用浏览器就能下单、查单、改状态、看物流。
>
> 系统采用 B/S 架构：数据库和 Flask 都部署在 Linux 虚拟机上，数据库只监听本机，Windows 主机只通过 5000 端口访问订单列表和订单详情两个页面。
>
> 功能上分三层：**数据定义**，7 张业务表加 1 张日志表，覆盖 1-1、1-N、N-M 三种联系，达到 3NF；**数据操纵**，建表、增删改查、删表、多表连接、分页筛选都能实际跑；**核心机制**，下单在一个事务里完成插订单、扣库存、生成物流单，失败整体回滚，用行锁加条件更新防超卖，取消订单回补库存，还做了联合索引、EXPLAIN 对比和 1 到 50 客户端并发测试。

### 1.2 时间够再补（约 55 字）

> 安全上所有 SQL 都参数化，运行时账号只有增删改查权限；封板实测 16.2 万行（含并发测试追加数据时 18.2 万行），客户订单查询加索引后从 3.340 毫秒降到 0.049 毫秒。

### 1.3 30 秒精简版（被要求压缩时用）

> 这是给中小电商用的订单与仓储管理系统，解决人工登记导致的数据重复、库存不准、订单和物流脱节。PostgreSQL 存客户、商品、分类、订单、明细、物流 7 张表，Flask 做 B/S 访问，两个页面。核心功能是订单增删改查和多表关联查询，以及用事务保证下单扣库存、生成物流单一致，配合索引优化、EXPLAIN 和多客户端并发测试。

### 1.4 讲稿的"扣题"点（老师打分看这些）

| 考核点 | 稿中对应句 |
|---|---|
| 应用场景 | 中小电商；表格登记的 3 个痛点；运营/仓储/配送人员 |
| 系统功能 | 数据定义 / 数据操纵 / 核心机制三层 |
| 与实际工作挂钩 | 下单、查单、改状态、看物流、库存账实一致 |
| 数据库味 | 事务、回滚、行锁、3NF、索引、EXPLAIN、并发、参数化 |

## 二、系统一页纸（功能全景）

| 层次 | 功能 | 落地位置 |
|---|---|---|
| 部署 | B/S，双机独立 IP；PG 只听 `127.0.0.1:5432`，Flask 听 `0.0.0.0:5000`，UFW 只开 5000 | `README.md` 第 5~6 节、`docs/07_deployment.md` |
| 数据定义 | 8 张表（7 业务 + `access_log`）、主键/外键/唯一/CHECK/触发器 | `sql/01_schema.sql` |
| 数据规模 | 8 表合计 **162165** 行（封板实测，>10 万；含并发测试追加数据时 182460 行），合成数据 | `scripts/seed_data.py`、`tests/test_db_counts.sql` |
| 建模 | 6 实体；1-1 订单—物流、1-N 客户—订单、N-M 商品—分类；3NF | `docs/02_erd.md` |
| 数据操纵 | 商品增/改/删/查；订单创建/状态修改/明细删除/删表演示 | `app/repositories/products.py`、`orders.py` |
| 查询 | 订单列表筛选分页、订单详情多表 join、N-M 分类聚合 | `app/repositories/orders.py` 的 4 条 SQL |
| 事务 | 下单事务、取消回补、删除明细回补、异常整体回滚 | `app/db.py` 的 `transaction()` |
| 索引 | 7 个二级索引；EXPLAIN 前后各 3 次 | `sql/02_indexes.sql`、`sql/07_explain.sql` |
| 并发 | 1/10/25/50 客户端，70% 读 / 20% 写 / 10% 更新 | `scripts/benchmark_concurrency.py` |
| 安全 | 参数化 SQL、CSRF、两个最小权限账号、端口隔离、访问日志 | `app/security.py`、`app/__init__.py`、`sql/00_bootstrap_roles.sql` |
| 页面 | 订单列表页、订单详情页（课程要求 1~2 个） | `app/templates/`、`app/static/` |

**架构一句话**：Windows 浏览器 →（HTTP 5000）→ Linux VM 上的 Flask →（psycopg2 原生 SQL，本地 5432）→ PostgreSQL。

## 三、随机功能提问应答卡

> 回答统一用四步：**实际工作里谁用/解决什么 → 我怎么做的（表/SQL/代码） → 怎么验证（页面/命令/截图） → 边界或改进**。
> 下面每条都可直接照着说；"现场演示"一列是被追问时最有力的动作。

### 1. 建表 / 数据定义（DDL）

- **实际工作**：新业务上线要建客户、商品、订单表；字段规则要落到数据库，不能只靠页面校验。
- **我怎么做的**：`sql/01_schema.sql` 由 `db_owner` 执行，8 张表带主键、外键、唯一、CHECK 和 `updated_at` 触发器；`scripts/init_db.py create-tables` 可重复建库。
- **一句话答**："建表不是只写 CREATE TABLE，我把业务规则也写进约束了，比如 `stock >= 0`、`quantity > 0`、状态枚举、邮箱唯一。"
- **现场演示**：`\dt` 列 8 张表；`\d orders` 看约束；故意插负库存被 CHECK 拒绝。

### 2. 插入数据（创建订单）

- **实际工作**：运营接到客户下单，要一次性登记订单头、多条明细、扣库存、生成物流单，漏一步就账实不符。
- **我怎么做的**：`POST /api/orders` → `app/repositories/orders.py::create_order()`，一个 `transaction()` 内：校验客户 → INSERT orders → 对每个商品 `SELECT … FOR UPDATE` → `UPDATE … WHERE stock >= qty` → INSERT order_item → INSERT shipment（运单号 `TRK-订单号-随机码`）。同商品重复提交先合并数量。
- **一句话答**："四张表的写入放在同一个事务里，COMMIT 才一起可见，任一步失败全部回滚。"
- **现场演示**：列表页"创建订单"，选 2 件商品提交，再打开详情看到明细和物流单；`SELECT COUNT(*) FROM orders` 前后对比。
- **边界**：一次最多 50 种商品、总数量 10000，地址留空用客户默认地址。

### 3. 修改数据（订单状态机）

- **实际工作**：客服把未支付改成已支付、仓储发货改成已发货，不能让人从"待支付"直接跳到"已发货"。
- **我怎么做的**：`PATCH /api/orders/<id>/status`，`TRANSITIONS` 字典限制 `PENDING→PAID/CANCELLED`、`PAID→SHIPPED/CANCELLED`、`SHIPPED→COMPLETED`；先 `SELECT … FOR UPDATE` 锁订单再判断；发货/完成时同步把物流单改成 `IN_TRANSIT` / `DELIVERED`。数据库里还有 CHECK 约束兜底。
- **一句话答**："状态流转是白名单，非法流转返回 409；锁订单保证两个人同时改状态时串行判断。"
- **现场演示**：列表页把 PENDING 改 PAID 成功，再直接改 SHIPPED 看 409。

### 4. 删除数据（删明细、删商品、删表）

- **实际工作**：客户临时去掉一件商品，库存要还回去；已卖过的商品不能随便删，否则历史订单查不到。
- **我怎么做的**：`DELETE /api/order-items/<id>` 只允许 PENDING/PAID，回补该商品库存，且订单至少保留一条明细；`DELETE /api/products/<id>` 被订单明细引用时返回 409（外键 `ON DELETE RESTRICT`）；删表用 `sql/06_drop_table_demo.sql` 建 `demo_drop_me` 再 DROP，不动 7 张核心表。
- **一句话答**："业务删除优先回补库存，物理删除有外键和状态双重保护，删表只演示在临时表上做。"
- **现场演示**：详情页删一条明细 → 查 `product.stock` 增加；删已引用商品 → 409；`\dt` 前后对比。

### 5. 多表连接查询（订单详情）

- **实际工作**：仓储拣货和客服对账要在一屏看到客户、买了什么、属于哪些分类、发哪个物流、一共多少钱。
- **我怎么做的**：`app/repositories/orders.py` 里 `ORDER_HEADER_SQL`（orders⋈customer⋈shipment）、`ORDER_ITEMS_SQL`（order_item⋈product⋈product_category⋈category，`string_agg` 聚合分类）、`ORDER_SUMMARY_SQL`（SUM 汇总金额）；列表页那条 SQL 用 LEFT JOIN + GROUP BY 一次算出金额和明细数。
- **一句话答**："详情是 6 张表的 join，金额用 `SUM(quantity*unit_price)` 现算，不存冗余总额，这样改明细不会算错，也符合 3NF。"
- **现场演示**：打开 `/orders/<id>` 逐项对照页面字段与 SQL 输出。
- **坑要会答**：N-M join 可能放大行数，所以用 `string_agg` 聚合分类、列表用 GROUP BY，避免重复计算金额。

### 6. 事务、提交与回滚（高频）

- **实际工作**：下单扣了库存但订单没建成，就是最典型的"半单"，仓库会少货。
- **我怎么做的**：`app/db.py::transaction()` 成功 commit、异常 rollback、`finally` 归还连接；`tests/test_transaction.py` 用两个会话验证提交可见 / 回滚不可见。
- **一句话答**："我的回滚不是靠代码删数据，是靠数据库事务；库存不足时 `rowcount != 1` 抛业务异常，整单回滚，订单头、明细、库存、物流都不留痕迹。"
- **现场演示**：选一个低库存商品、数量填超过库存提交 → 页面提示"库存不足" → 前后查 `COUNT(*) FROM orders` 和商品库存，都没变（对应 `防超卖报错图.png`、`docs/evidence/TX-03/`）。

### 7. 并发与防超卖（高频）

- **实际工作**：多人同时抢最后几件货，不能卖出负库存。
- **我怎么做的**：先 `SELECT product … FOR UPDATE` 锁商品行，再 `UPDATE product SET stock = stock - %s WHERE product_id = %s AND stock >= %s`，检查影响行数为 1；隔离级别用 PostgreSQL 默认 READ COMMITTED，行锁 + 条件更新已够，没上 SERIALIZABLE。
- **一句话答**："检查和扣减放在同一条带条件的 UPDATE 里，数据库保证原子性；失败就回滚，50 并发实测库存没有出现负值。"
- **现场演示**：跑 `scripts/benchmark_concurrency.py`；`SELECT * FROM product WHERE stock < 0` 应为 0 行。

### 8. 取消订单 / 库存回补与幂等

- **实际工作**：客户取消后要立刻把货放回可售库存，重复点取消不能把库存加两遍。
- **我怎么做的**：`update_order_status()` 锁订单，仅 PENDING/PAID 可取消；已是 CANCELLED 直接返回（幂等）；只有从非取消态变成 CANCELLED 才用 `UPDATE product p SET stock = p.stock + oi.quantity FROM order_item oi …` 一次性回补，并写 `cancelled_at`。
- **一句话答**："回补和改状态在同一事务，状态是终态，所以重复取消不会重复加库存。"
- **现场演示**：取消前后查同一商品库存，再点一次取消，库存不变。

### 9. 索引与 EXPLAIN（高频）

- **实际工作**：16 万余行里查某个客户的历史订单，全表扫会慢。
- **我怎么做的**：`sql/02_indexes.sql` 建 7 个索引，核心是联合索引 `idx_orders_customer_created (customer_id, created_at DESC)`——等值列在前、排序列在后；`sql/07_explain.sql` 在同一查询上先删索引跑 3 次、再建索引跑 3 次，`EXPLAIN (ANALYZE, BUFFERS, VERBOSE)`。
- **一句话答**："实测计划从 Seq Scan 变成 Bitmap Index Scan，耗时 3.340 ms → 0.049 ms，约 68 倍；但我不认为加了索引就一定快，选择度低、统计信息过期、`LIKE '%x%'` 都可能走全表扫，一切以 EXPLAIN 为准。"
- **现场演示**：打开 `docs/evidence/IDX-01/explain_plan.png`，或现场跑一次 `07_explain.sql`。
- **加分**：索引有写放大代价，所以只建 7 个，不给低选择度的布尔列单独建索引；建完要 `ANALYZE`。

### 10. 多客户端并发与性能

- **实际工作**：要回答"这套系统能撑多少运营同时用"。
- **我怎么做的**：自写 `scripts/benchmark_concurrency.py`，每客户端独立 `psycopg2.connect`，1/10/25/50 并发，每级 30 秒 + 5 秒预热，70% 读、20% 写、10% 更新；逐条记录延迟、成功/失败、SQLSTATE，输出 CSV 和 summary JSON。
- **一句话答**："实测 10 并发 TPS 1177.5，50 并发 p95 135.243 ms，错误率约 1.8%；这些失败主要是库存不足触发的业务回滚，不是数据库故障，恰恰证明防超卖生效了。"
- **现场演示**：`docs/evidence/CON-01/` 的 CSV/JSON/截图；测试后查 `pg_stat_activity` 确认无 `bench_*` 残留连接。
- **必答**：还要核对无半单（订单无明细 0 行）、无重复物流单（按 order_id 分组 count>1 为 0 行）、无负库存。

### 11. 安全：SQL 注入、权限、端口

- **实际工作**：Web 系统直接暴露给浏览器，不能让输入框拼进 SQL，也不能让 Web 账号能删表。
- **我怎么做的**：所有值用 `%s` 占位符（`app/repositories/*.py` 全篇无字符串拼 SQL），`IN` 用 `= ANY(%s)`，动态标识符只来自白名单；写接口要 CSRF token；`app_rw` 只有增删改查权限、`db_owner` 非超级用户管 DDL，`postgres` 只在 bootstrap 用一次；PG 只监听 127.0.0.1，UFW 只开 5000。
- **一句话答**："输入 `' OR '1'='1` 只会被当成字面值；用 app_rw 执行 `DROP TABLE orders` 会报 permission denied；Windows 上连 5432 应该超时。"
- **现场演示**：筛选框输入注入串；`docs/evidence/SEC-03/permission_denied.png`；`Test-NetConnection <VM_IP> -Port 5432`。

### 12. 数据模型：三种联系与 3NF

- **实际工作**：一个订单只能有一张物流单、一个商品能属于多个分类、订单总额不该另存一份。
- **我怎么做的**：1-1 靠 `shipment.order_id UNIQUE` + 外键；1-N 靠 `orders.customer_id`、`order_item.order_id`；N-M 靠 `product_category(product_id, category_id)` 复合主键；3NF 靠不存订单总额、行金额、客户姓名、分类名，`order_item.unit_price` 是下单时的价格快照（历史价，不是冗余）。
- **一句话答**："6 个业务实体、1 张联系表、1 张运维日志表，主键 `(order_id, product_id)` 保证同订单同商品只有一条明细，`order_item_id` 只是给删除接口用的唯一代理列，没有改主键。"
- **现场演示**：给已有物流单的订单再插一条 shipment → 唯一约束报错；`docs/evidence/AC-DB-05/ERD.png`。

### 13. 分页、筛选、健康检查、访问日志

- **实际工作**：运营每天只查"某个客户、某状态、某段时间"的订单；系统出问题要能快速判断是应用还是数据库。
- **我怎么做的**：`GET /api/orders` 支持 `customer_id`/`status`/`date_from`/`date_to`/`page`/`page_size`，用 `(%s IS NULL OR …)` 参数化实现可选条件，`page_size` 上限 100，先 `COUNT(*)` 再 `LIMIT/OFFSET` 并按 `created_at DESC, order_id DESC` 稳定排序；`/health` 查应用与数据库连通；`after_request` 把方法、路径、状态码、耗时、客户端 IP 写进 `access_log`，写日志失败不影响业务。
- **一句话答**："筛选和分页都在 SQL 层做，排序带主键保证翻页不重复不漏行；日志只记路径不记查询参数，避免敏感信息。"
- **现场演示**：列表页输入客户 ID 1 + 状态 PAID + 日期范围；访问 `/health`。

### 14. 连接池 / 为什么不用 ORM

- **实际工作**：多客户端并发时连接不能泄漏，也不能跨线程共用一条连接。
- **我怎么做的**：`app/db.py` 用 `ThreadedConnectionPool`（默认 1~20），`get_conn()` 用 `SELECT 1` 探活，`transaction()`/`connection()` 在 `finally` 里 `putconn`，归还前先 rollback，坏连接关闭；课程要求原生 SQL，所以不用 ORM。
- **一句话答**："不用 ORM 是因为要清楚展示每条 SQL、事务边界和 EXPLAIN，ORM 会把这些藏起来。"
- **现场演示**：并发测试后 `pg_stat_activity` 无残留连接。

## 五、答题万能套路与兜底话术

**四步模板**：
1. "在实际业务里，这个功能是给……用的，解决……问题"；
2. "我在项目里是这么做的：表/字段/SQL/代码在……"；
3. "验证方式是……（页面操作或命令），结果在 `docs/evidence/…`"；
4. "边界是……，如果继续做可以……"。

**被问到没做过 / 没测过**：
