## 1. 1 分钟讲稿（约 230 字，照读）

我做的是一个面向中小电商的**订单与仓储管理数据库应用**。原来用表格人工登记，数据重复、库存账实不符、订单和物流对不上，所以把客户、商品、分类、订单、明细、物流单统一放进 PostgreSQL，运营和仓储人员用浏览器就能下单、查单、改状态、看物流。

系统采用 B/S 架构：数据库和 Flask 都部署在 Linux 虚拟机上，数据库只监听本机，Windows 主机只通过 5000 端口访问订单列表和订单详情两个页面。

功能上分三层：**数据定义**，7 张业务表加 1 张日志表，覆盖 1-1、1-N、N-M 三种联系，达到 3NF；**数据操纵**，建表、增删改查、删表、多表连接、分页筛选都能实际跑；**核心机制**，下单在一个事务里完成插订单、扣库存、生成物流单，失败整体回滚，用行锁加条件更新防超卖，取消订单回补库存，还做了联合索引、EXPLAIN 对比和 1 到 50 客户端并发测试。

> 时间够再补：所有 SQL 参数化，运行时账号只有增删改查权限；封板实测 16.2 万行（含并发测试追加数据时 18.2 万行），加索引后查询从 3.340 ms 降到 0.049 ms。

## 3. 必背硬核数字

| 数字 | 一句话解释 |
|---|---|
| **8 张表 / 6 个实体** | 7 张业务表 + `access_log` 运维表；1-1、1-N、N-M 全覆盖，达到 3NF |
| **162165 行（16.2 万）** | 封板重新 seed 后 8 表 `COUNT(*)` 实测；含并发测试追加数据时达 182460 行（18.2 万），两者均 >10 万 |
| **3.340 ms → 0.049 ms（约 68 倍）** | 客户订单历史：加联合索引后 `Seq Scan` → `Bitmap Index Scan` |
| **10 并发 TPS 1177.5** | 自写脚本，1/10/25/50 客户端，70% 读 / 20% 写 / 10% 更新 |
| **50 并发 1.8% 失败率** | p95 135.243 ms；失败是**库存不足的业务回滚**，不是数据库故障 |
| **5000 / 127.0.0.1:5432** | 只对外开放 5000；数据库不对外，`app_rw` 仅 DML |

数字全部来自 Linux VM 实测，证据在 `docs/evidence/`；**不报没测过的 TPS**。

## 4. 四大实操演示路径

**① 正常下单（30 秒）**
列表页 → 客户 ID 填 `1` → 商品下拉挑一个**库存 ≥ 2** 的商品（下拉项会显示库存）→ 数量 `2` → 添加明细 → 创建订单。
看到：绿色「订单创建成功 #…（库存已扣减，物流单已生成）」。
说：**"插订单、插明细、扣库存、生成物流单 4 张表的写入在一个事务里，COMMIT 才一起可见；这是运营每天下单的实际流程。"** 点进详情可看到 1-1 物流单。
> 别选商品 10（库存 5，留给下一项演示）。

**② 防超卖 / 事务回滚（重点，40 秒）**
新建订单 → 商品搜索输入 `0010` 选中商品 10（库存 5）→ 数量填 `10` → 创建订单。
看到：**红色「商品 10 库存不足」**。
说：**"`SELECT … FOR UPDATE` 锁商品行，再执行 `UPDATE product SET stock = stock - 10 WHERE product_id = 10 AND stock >= 10`，影响 0 行就抛业务异常，整个事务 ROLLBACK —— 订单头、明细、库存、物流都不留痕迹，仓库不会出现半单。"**
补刀：前后 `SELECT COUNT(*) FROM orders` 和商品库存都不变；证据 `docs/evidence/TX-03/`、`防超卖报错图.png`。
> 若提示「商品已下架」而非「库存不足」：prepare 脚本未跑成功，重跑第 2 步即可。

**③ 订单详情：6 表 join（30 秒）**
列表点订单号 → 逐项指出客户、明细、商品、分类、物流、金额汇总。
说：**"这是 orders/customer/order_item/product/product_category/category/shipment 的多表 join，仓储拣货和客服对账就看这一屏。总金额是 `SUM(quantity * unit_price)` 实时算的，不存订单总额，改明细不会算错，也符合 3NF；分类用 `string_agg` 聚合，避免 N-M join 放大行数。"**

**④ 索引展示（终端，30 秒）**
```bash
psql -h 127.0.0.1 -U db_owner -d course_db -f sql/07_explain.sql
```
指出输出里的 `Seq Scan` → **`Bitmap Index Scan`**，以及耗时 3.340 → 0.049 ms。
说：**"索引是 `(customer_id, created_at DESC)`，等值列在前、排序列在后；脚本在同一查询上删索引跑 3 次、建索引再跑 3 次，用 `EXPLAIN (ANALYZE, BUFFERS, VERBOSE)` 对比，结论以执行计划为准。"**

## 5. 高分话术与避坑

| 老师问到 | 标准话术 |
|---|---|
| 50 并发 1.8% 失败 | **"是库存不足触发的业务事务回滚，不是数据库故障，恰恰证明防超卖拦截生效；库存始终无负值、无半单、无重复物流单、无连接泄漏。"** |
| 索引一定更快吗 | **"不一定，以 EXPLAIN 为准。"** 选择度低、统计信息过期、表太小、`ILIKE '%q%'` 都可能走全表扫；索引还有写放大，所以只建 7 个，建完 `ANALYZE`。 |
| 权限 / 登录 | **"只做了数据库层最小权限：`app_rw` 仅 DML、`db_owner` 非超级用户、5432 只监听本机、UFW 只开 5000；没有完整登录和多角色权限，这是已知限制，列入后续改进。"** 不要说成已实现登录。 |
| 为什么不用 ORM | 课程要求原生 SQL；要清楚展示每条语句、事务边界、连接释放和 EXPLAIN，ORM 会藏起来。 |
| 没做过的 / 没测的 | "这块没有实现/没有实测，我不编数据；要验证我会现场跑一条 SQL 或 `docs/demo_flow.md` 第 X 步。" |
| 任何数字 | "这个数字来自 `docs/evidence/<AC-ID>/` 的原始输出/CSV/截图。" |

**别说错**：不加「索引一定更快」；不把业务失败说成故障；不声称做了完整登录、购物车、支付或 NoSQL 部分；`SHIPPED`/`COMPLETED` 不能直接取消。

**现场故障预案**：页面 503 → 查 `/health` 与 PostgreSQL 服务；CSRF 403 → 刷新页面取新 token；状态 409 → 对照状态机；列表无数据 → 重跑 prepare 脚本；不展示 `.env` 和真实密码，不现场改代码。
